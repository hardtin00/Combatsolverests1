## 11. 发现一个真实限制：能量正好为 0 时，引擎直接结束回合

复现步骤（可控局面）：

```
能量 0，手里只有 CLASH（0 费，14 伤害）  → 路线 = END_TURN
能量 1，手里只有 CLASH                    → 路线 = PLAY_CARD CLASH
能量 0，手里只有 BLOODLETTING（0 费）     → 路线 = END_TURN
能量 0，手里只有 DEFEND_RED（1 费）       → 路线 = END_TURN（这张本来就不能打，正确）
能量 0 + 对面 300 血、3000 次模拟         → 仍然是 END_TURN
```

也就是说：**只要当前能量是 0，引擎就不会再考虑任何出牌，哪怕手里有 0 费牌**。
游戏里 0 费牌（Clash、Seeing Red、Bloodletting、Flex…）在 0 能量时是能打的，
所以这种情况下求解器会少打一张牌。

它不会产生非法操作（结束回合永远合法），只是偏保守。
根因没定位到（引擎的动作枚举里没有 `energy == 0` 的短路，`CardInstance::canUse` 对 0 费牌也是放行的），
所以这一条按"已知限制"记录，不去改动冻结的搜索核心。

## 12. 选牌之后的路线是否还连续（头槌那类牌）

用户最早报的现象是"头槌选完牌之后又自己停下来了"。当时定位到三个叠在一起的原因，其中一个是
适配器把"选牌"这个动作当成了路线里的一步（`hand_slot=-1` 的假步骤），走完选牌后路线对不上、
执行就停了。

这次用三张会开选牌界面的牌单独造局面，直接看引擎返回的路线：

| 牌 | 打出的牌序（前几步） | 假步骤 | valid | replay |
|---|---|---|---|---|
| 头槌 HEADBUTT | 打击 → 回合结束 → **从弃牌堆拿回的打击** → 头槌 → 打击 | 0 | True | True |
| 军备 ARMAMENTS | 军备 → 强化后的打击（同一回合） | 0 | True | True |
| 发掘 EXHUME | 发掘 → **从消耗堆拿回的重击** → 打击 | 0 | True | True |

关键证据是 uuid：头槌那条路线里第二回合打出的 `BASH`，uuid 是 `…0040`——
正是我放进弃牌堆的那张。发掘那条里是 `…0070`——放进消耗堆的那张。
说明选牌这个动作**真的在树里执行了**（牌被从弃牌/消耗堆移到了手里），
只是没有作为路线里的一步暴露出来。路线接着往下走，没有停。

三个局面都是 `status=SEARCHED / valid=True / replay=True / truncated=[]`。

## 13. 药水：文档说"会被搜索考虑"，实际是关的

对着适配层源码查了一遍 `_build/cs1_search.cpp`：

```cpp
// 210 行附近
bc.potionCapacity = 0;
bc.potionCount = 0;
for (auto &slot : bc.potions) slot = Potion::EMPTY_POTION_SLOT;
...
// 530 行附近
out["potion_actions"] = json::object();
out["potion_actions_mode"] = "off";
```

也就是说**无论采集到几瓶药水，引擎都按"没有药水"来搜**。实测印证：

```
局面：手里 [打击, 防御]，药水 [Block Potion, Fire Potion]，能量 3，玩家 40 血
命令：--execution-potions "Block Potion,Fire Potion"
结果：potion_actions_mode=off，candidate_route 全是 PLAY_CARD / END_TURN，没有一步喝药
```

所以 `使用说明.md` 原来那句"确定性药水会被搜索考虑"、README 里"药水完成"那一行、
`KNOWN_LIMITS` 第 4 条，都是假的，这一轮改成了实话：**求解器不喝药，药水手动喝**。

要接回药水，工作量大概是：把 `Potion` 枚举（56 个值）做成 id 映射、按采集结果填
`bc.potions` / `potionCount` / `potionCapacity`、把 `potion_actions_mode` 改成真实值、
再让路线产出 POTION 步骤。不是不能做，但这是一次行为改变（求解器会开始主动喝药），
得单独验证一轮，不能顺手塞进这版。

## 14. 遗物和药水在引擎里的落地情况

卡牌是跑局面逐张验的，遗物和药水改用源码级统计：把 `engine-source` 里 `bindings/`（pybind 导出的
名字表）和 `constants/`（枚举、名字数组、id 映射）排除，只数 `src/` 和 `include/` 里的真实引用。

| 类别 | 表里数量 | 战斗/搜索代码里被引用 | 结论 |
|---|---|---|---|
| 遗物 `RelicId` | 180 | **180** | 每个遗物都至少有一处行为代码，不是只有枚举和名字 |
| 药水 `Potion` | 43 | **43** | 引擎本来就实现了药水 |

抽样核对过，不是"只出现在名字表里"那种假阳性：

```
src/combat/Monster.cpp:389   if (bc.player.hasRelic<RelicId::THE_BOOT>() && damage > 0 && damage < 5)
include/combat/BattleContext.h:323  if (s == MS::VULNERABLE && player.hasRelic<RelicId::CHAMPION_BELT>())
src/combat/VictoryHp.h:43    case RelicId::BURNING_BLOOD: if (hp > 0) heal(6); break;
```

顺带把第 13 节的结论补完整：药水不是"没实现"，是**适配层主动关掉的**

## 15. 换一台电脑就起不来：引擎缺 VC++ 运行库

查引擎 exe 的导入表（直接扫二进制里的 dll 名）：

```
MSVCP140.dll
VCRUNTIME140.dll
VCRUNTIME140_1.dll
api-ms-win-crt-*.dll        （这几个是 Windows 自带的 UCRT）
```

前三个是 **Visual C++ 2015-2022 运行库**，不是 Windows 自带的。本机因为装过 VS BuildTools 所以能跑；
换一台干净的电脑（只装了 Steam 和游戏），`VCRUNTIME140_1.dll` 很可能不存在，引擎一启动就报
"找不到 vcruntime140_1.dll"，面板也起不来——正好是"别人装了就报错"那类问题。

处理办法：把运行库随包发（app-local），从 VS 的官方 redist 目录取，不用别人装 redist：

```
VC/Redist/MSVC/14.44.35112/x64/Microsoft.VC143.CRT/
    msvcp140.dll         557,728
    vcruntime140.dll     124,544
    vcruntime140_1.dll    49,792
```

三个 dll 和 exe 放同一目录，Windows 会优先用 exe 旁边的那份。已经放进
`<游戏>\cs1-engine\` 和交付包的 `engine\`，`START_HERE.md` 第 2 步改成"5 个文件全部放进去"。

验证：加上 dll 之后再跑一次引擎（50 次模拟），`SEARCH_RESULT` 正常产出，退出码 0。
自检脚本 `_build/final_check.py` 里也加了一条检查：三个 dll 必须同时出现在交付包和安装目录。

顺带删掉了 `cs1-engine` 里两个旧引擎备份（`s2b0_search_3d.exe.bak-2louse`、`.bak-legacy`，共 2.7 MB）——
那是 A/B 对比用的中间产物，交付包里已经有正式 exe。

## 17. 面板自身的两个隐患（已修）

面板从来没在真机上显示过，所以这一轮改成读代码找"会让面板整个不出现"的地方。

**隐患一：血条计数器能把面板一起弄死。** 原来 `render()` 是这样：

```java
try {
    HpTracker.update();
    draw(batch);
} catch (Throwable error) { report(error); }
```

`HpTracker.update()` 每帧都跑，而且跑在"是不是在战斗里"这些判断**之前**。它里面调
`AbstractDungeon.getCurrRoom()`，只要它在某个画面（切场景、读档、结算）抛一次，`draw()` 就整个被跳过——
面板直接不显示，而且 `report()` 五秒才记一条日志、最多记 20 条，很容易看起来"什么都没发生"。

改成两个独立的 try：计数器挂了只影响那三个数（保留上一帧的值），面板照常画。

**隐患二：收起状态下点标题栏可能误触按钮。** 按钮的矩形是在画的时候填进 `buttonRects` 的，
收起时按钮不画，但 `buttonRects` 还留着展开那一帧的旧矩形。如果这时点在标题栏上，
命中判定可能拿旧矩形去比，触发一个看不见的按钮（比如"执行一项"）。收起分支里补了一句
`buttonRects.clear()`。

改完的验证：

```

LoadAll2           →  loaded=238 failed=0 total=238
PanelLangTest      →  PANEL_LANG_OK

installed = delivered（游戏里的 jar 与交付包里的 jar 同一个哈希）
final_check        →  ALL CHECKS PASSED
```

只换了 `IsolatedMctsPanel.class` 这一个条目，其余 238 个条目是原封不动拷过去的。

### 这里改掉了一个真实的重复计数

第一版跑出来两条红：

```

FAIL campfire heal not counted expected 3 got 5
```

原因是 StS 里"最大生命 +2"会**同时把当前生命也 +2**（Fruit Juice 就是这种）。旧代码把当前生命
这 +2 记进了"回复"，于是同一瓶药在面板上同时出现在「回复 +2」和「最大生命 +2」里——重复计一次。
用户要的是两件不同的事（"战斗全过程回血" vs "最大生命值提升（吃最大生命药水等）"），所以改成本
次的最大生命增量从回血里扣掉：

```java
int maxDelta = (lastMax >= 0 && player.maxHealth > lastMax) ? player.maxHealth - lastMax : 0;
if (maxDelta > 0) maxGain += maxDelta;
if (player.currentHealth > lastHp) {
    int up = player.currentHealth - lastHp;
    healing += Math.max(0, up - maxDelta);   // 最大生命带来的那部分是 maxGain，不是回血
}
```

## 20. 选牌最关键的修复，也上测试了：settle() 不会卡住、也不会一闪而过

用户最早的两个抱怨是"选完牌自动执行停住"和"选牌太快，看不清就没了"。修的时候改的是
`SelectPick.settle()`（`AutoVerifyGate.verify` 每次执行动作前都会调它）。这一节把它放到桩里跑。

桩：`SelectGlue`（pending/resolve）、`SelectScreenDriver`（screenName/gridCards/handCards/
expectedCount/commit）、`AbstractCard`。测试类 `SelectPickTest`。

**15 条断言全过（`SELECT_PICK_OK`）：**

```
没有待选牌        settle() 直接返回 false，6ms 内结束，不 spawn 任何副作用
有待选牌          resolve 调用 1 次，总耗时 665ms（>=650 的展示延迟被遵守）
resolve 生效后    不再强制提交
resolve 没关掉界面 走 directCommit 兜底：commit 调用 1 次、提交 1 张、总耗时 652ms（<3000）
界面里没有牌     不提交，直接返回
```

三条关键结论：

1. **不会卡住**：无论 resolve 成不成功，函数都在约 650ms 内返回，且屏幕还开着时一定有兜底提交
   （提交数量取 `expectedCount()`，至少 1）。这就是"自动执行停住"的根因修复。
2. **不会一闪而过**：`REVEAL_MS = 650` 的等待确实发生（665ms/652ms 实测），牌能被看见。
3. **没有待选牌时零开销**：6ms 返回，不调用任何游戏接口——不会在每回合每张牌上无故停顿。

写入的 `select-gate.log` 形如：

```
1793737603174 screen=GridCardSelectScreen cards=1 forced=false stillOpen=false after=GridCardSelectScreen refusal=null
```

`forced=true` 表示这次是兜底选的（界面没自己关掉），排查时看这个字段。

## 26. 战斗结束那一刻面板会消失——于是"打完回的血"永远看不见

第 25 节把战损的数字修对了，这轮顺着②的要求查"战斗全过程回血"。

`HpTracker` 的注释写得很清楚：它统计**含开战和结束**的回血（燃烧之血打完回 6、回血药、遗物）。
但面板的可见条件是这样的（`IsolatedMctsPanel.draw()`）：

```java
if (room.phase != AbstractRoom.RoomPhase.COMBAT) return;
```

战斗一结束，房间阶段从 `COMBAT` 变成 `COMPLETE`，面板立刻消失——而那 6 点血是在这之后加的。
结果是：这个数字被算出来了，却永远显示不出来。等于②里的"结束回血"在界面上不存在。

### 改法

把可见条件放宽到"同一场战斗的奖励界面也算":

```java
private static boolean inCombatOrReward(AbstractRoom room) {
    if (room.phase == AbstractRoom.RoomPhase.COMBAT) return true;
    if (room.phase != AbstractRoom.RoomPhase.COMPLETE) return false;
    try {
        return AbstractDungeon.screen == AbstractDungeon.CurrentScreen.COMBAT_REWARD;
    } catch (Throwable ignored) {
        return false;
    }
```

## 28. 自动执行被拒绝后自己重启（带上限），顺便纠正第 27 节的一个错判

### 28.1 先纠正：自动执行**会**结束回合

第 27 节我写了"`action_executed` 204 条全是出牌，从不结束回合"。这个结论错了——我只看了动作日志。
真机的状态机日志里明明有：

```
READY_TO_EXECUTE -> END_TURN_PENDING   ×74   「MCTS 推荐结束回合，实体点回合按钮提交一次」
END_TURN_PENDING -> MONSTER_TURN_WAIT  ×74   「结束回合已提交，怪物回合期间不提交任何玩家动作」
```

结束回合是单独一条通路，不写进 `action_executed`。所以"不会结束回合"这条作废，
`KNOWN_LIMITS.md` 第 11 条已经改回正确说法。

### 28.2 真正让自动执行停下来的原因

状态机的最后几步：

```
READY_TO_EXECUTE -> EXECUTING          提交一张合法卡牌
EXECUTING -> WAITING_FOR_IDLE          等待原生结算
WAITING_FOR_IDLE -> VERIFYING          重新采集真实状态并与预测对照
VERIFYING -> REFUSED                   重采失败，无法确认新状态，自动执行停止
```

`VERIFYING -> REFUSED` 就是"停住"的真凶：打完一张牌后重采状态，采回来的和预测对不上，
状态机为了安全直接停机。停机本身是对的（宁可不打，不能乱打），但**它不会自己恢复**，
玩家看到的是一块写着 Idle 的面板 + 一条路线，然后什么也不发生。

### 28.3 改法：有上限的自愈

面板每帧看一眼会话状态，发现 `REFUSED` 就等 2.5 秒重新授权一次（`armAutoExecution()`）：

```java
int actions = session.autoActionsExecuted();
if (actions > lastActionsSeen) { lastActionsSeen = actions; reArmCount = 0; }  // 有进展就还预算
if (state == null || !state.contains("REFUS")) return false;
if (room.phase != AbstractRoom.RoomPhase.COMBAT) return false;
if (reArmCount >= REARM_LIMIT) return false;            // 一场最多 8 次
if (now - lastReArmAt < REARM_GAP_MS) return false;      // 间隔 2.5 秒
```

`CS1_ISOLATED_NO_REARM=true` 可关。面板同时把 `REFUSED` 显示成 `Stopped`，
不再假装 `Idle`。

### 28.4 这一版我自己先踩了个坑（记下来）

第一版把预算的复位条件写成"状态不再是 REFUSED"，结果：重新授权会让状态离开 REFUSED 一帧 →
预算被清零 → 下一次拒绝又变成第 1 次 → **每帧重授权一次**。真机上 90 秒写了 16356 行日志
（`re-arm after refusal #1` × 16392），等于空转。

`#1/8 … #8/8` 各一行，一共 9 行。回归测试也补了这条（模拟 40 帧状态来回抖动，断言重授权次数不超过上限）。

## 29. "自动打一下就停"的真根因：拉格瓦林（Lagavulin）第 4 个招式没进映射表

### 29.1 先把现象量化

真机 trace 里 `event=refused` 一共 18247 条，按异常原文分组：

```
18223 | IllegalStateException: no verified engine move for LAGAVULIN native move 4
   10 | 采集被拒绝：无法采集当前战斗状态（请手动打完这一场）
    4 | 支持门控拒绝：NONE
    3 | IllegalStateException: unsupported monster power class/ID: ... SplitPower
    3 | UnsupportedClassVersionError: .../PowerWireMap   （旧 jar 残留，当前 jar 已无此问题）
    2 | IllegalStateException: monster power amount outside C++ storage range: SPLIT=-1
```

**18223 / 18247 = 99.9% 是同一句话**：拉格瓦林的原生招式 4 在引擎里找不到"已验证"的对应招式。
不是"重采抖动"，不是随机现象——是这一场战斗里每一次采集都会抛异常，于是每一次搜索都失败。

### 29.2 查证链

1. 游戏本体（`desktop-1.0.jar` → `monsters/exordium/Lagavulin.takeTurn`）的 `tableswitch 1..6`：
   1=吸血（SIPHON_SOUL）、3=普通攻击、**4=STUNNED**（只弹 `TextAboveCreatureAction.STUNNED` 然后
   `RollMoveAction`，不打人）、5=睡眠、6=OPEN 状态切换。
2. mod 的映射表 `MonsterWireMap.MOVES`（从 class 常量池还原）只有三条拉格瓦林：

```
LAGAVULIN|1 -> LAGAVULIN_SIPHON_SOUL
LAGAVULIN|3 -> LAGAVULIN_ATTACK
LAGAVULIN|5 -> LAGAVULIN_SLEEP          ← 缺 4
```

3. `MonsterWireMap.moveId(monster, n)` 就是 `MOVES.get(monster + "|" + n)`，返回 null；
   `LiveStateV1Capture` 拿到 null 就抛 `no verified engine move for ...`。
4. 引擎（`MonsterMoves.h`）里拉格瓦林只有 ATTACK / SIPHON_SOUL / SLEEP 三个，
   而 `MonsterSpecific.cpp` 里 SLEEP 的注释本身就是 "The damage-triggered stunned turn"——
   **引擎把"被晕住那一回合"就叫 LAGAVULIN_SLEEP**，语义和游戏里的招式 4 完全一致。

### 29.3 改法

重建 `MonsterWireMap`：把原来的 65 条怪物名 + 65 条类名 + 194 条招式映射原样搬过来，
**只加一条**：

```java
put(MOVES, "LAGAVULIN|4", "LAGAVULIN_SLEEP");   // the stunned turn
```

没有动引擎（引擎本来就认识 LAGAVULIN_SLEEP），也没有动 `VerifiedMoveEvidence`
（它已经有 LAGAVULIN_SLEEP）。

### 29.4 验证

`WireMapTest`（新增，198 条断言）：

```

```

- 194 条老映射逐条比对，一条不差（没有搬错、没有漏）；

- 并且 `VerifiedMoveEvidence.isVerified("LAGAVULIN_SLEEP") == true`——映射出来的名字确实在"已验证"集合里，

- 未知怪物仍然返回 null（没有把兜底逻辑写坏）。

## 32. 修好了："选目标"类技能把整场卡死（Spot Weakness / Disarm / Dark Shackles…）

### 32.1 根因（第 31 节那条门的下游）

引擎输出的路线长这样：

```
PLAY_CARD SPOT_WEAKNESS hand_slot=4 uuid=24be… target_slot=-1
```

但 Spot Weakness 是**技能里要选敌人**的那一类（同类还有 Disarm、Dark Shackles、Trip、Blind、
Malaise、Sucker Punch 之外的消耗牌等）。`target_slot=-1` 让 mod 的 `CardTargetRef` 解析不出目标，
第 5 道门报 `missing-selected-monster`，一个动作都不提交 —— 整场停住。

错在引擎适配层（`_build/cs1_search.cpp`）这一行：

```cpp
// 旧：只有 ATTACK 才带目标
const int targetSlot = card.getType() == CardType::ATTACK ? action.getTargetIdx() : -1;
```

用"卡牌类型"判断要不要目标本来就错，正确依据是这张牌自己声明的目标。引擎里有现成的：

```cpp
static constexpr bool cardTargetsEnemy(CardId id, bool upgraded);   // Cards.h:674
```

### 32.2 改法

```cpp
// 新：按牌自己的目标声明，不按类型
const int targetSlot = cardTargetsEnemy(card.id, card.upgraded) ? action.getTargetIdx() : -1;
```

一行，改的是我们自己的适配层，没动引擎算法，也没动 mod。

### 32.3 离线验证（6 个真实存档状态）

用改前/改后两个 exe 跑同一批 `live-battle-state-v1.seq12..17.json`（真实对局快照）：

| 状态 | 改前 | 改后 |
|---|---|---|
| seq12..17 | `SPOT_WEAKNESS target_slot=-1` | `SPOT_WEAKNESS target_slot=0` |

其余步骤逐字节相同，`candidate_route_all_actions_valid_in_tree_walk` 改前后都是 `true`，
路线长度 8 不变。也就是说：只补了缺的目标，没有把搜索带偏。

## 33. 修掉一个真会崩游戏的 bug：新开一局打完第一场就 NullPointerException

### 33.1 现象

全新开一局（不是读档），自动航行自己走到第一场小怪、打赢的那一瞬间，游戏直接崩：

```
java.lang.NullPointerException: null
	at com.megacrit.cardcrawl.saveAndContinue.SaveFile.<init>(SaveFile.java:349)
	at com.megacrit.cardcrawl.helpers.SaveHelper.saveIfAppropriate(SaveHelper.java:280)
	at com.megacrit.cardcrawl.dungeons.AbstractDungeon.nextRoomTransition(AbstractDungeon.java:2202)
	at com.megacrit.cardcrawl.dungeons.AbstractDungeon.updateFading(AbstractDungeon.java:2848)
	at com.megacrit.cardcrawl.core.CardCrawlGame.render(CardCrawlGame.java:423)
```

连续两次复现（06:25:46、06:31:43，都是"Removing monster: 2 Louse"之后 0.1 秒）。

### 33.2 定位

`SaveFile.<init>` 第 349 行对应的字节码是：

```java
this.current_room = AbstractDungeon.nextRoom.room.getClass().getName();
```

`nextRoom` 不是 null，`nextRoom.room` 是 null —— 于是 `getClass()` 崩。

那 `nextRoom.room` 为什么会是 null？看 `MapRoomNode.getRoom()`：

```java
public com.megacrit.cardcrawl.map.MapRoomNode.getRoom();
   0: aload_0
   1: getfield  #23   // Field room:Lcom/megacrit/cardcrawl/rooms/AbstractRoom;
   4: areturn
```

**它只是把这个字段返回出来**，字段本身在构造器里被设成 null，真正的房间对象要等
`AbstractDungeon.nextRoomTransition` 走到后面才创建（而且只对 `EventRoom` 那一路创建）。
我们的 `AutoPilot.enter()` 是这么走的：

```java
AbstractDungeon.nextRoom = node;
AbstractDungeon.nextRoom.room = node.getRoom();   // ← 这里就是 null
AbstractDungeon.nextRoomTransitionStart();
```

于是 nextRoom 带着一个 null 房间进入过场；过场里"保存进度"这一步排在"创建房间"前面，
读 `nextRoom.room.getClass()` 就崩。读档（continue）不崩，是因为存档里那些节点的房间对象
早就被上一次游戏进程创建过了 —— 这也解释了为什么前几轮读档跑几十层都没事。

### 33.3 改法

给 `AutoPilot.enter()` 加一道前置判断（字节码补丁 `_build/jar/PatchTravelGuard.java`）：

```java
if (node == null) return false;
if (node.getRoom() == null) return false;   // 房间还没建好的节点，不硬闯
```

不进入没有房间的节点，自动航行这一拍就跳过它；不会再出现"带着 null 房间进过场"的情况。

### 33.4 验证

同一套流程（清存档 → 新开 → 自动航行 → 打完第一场）：

| | 补丁前 | 补丁后 |
|---|---|---|
| 打完第一场小怪 | `NullPointerException`，游戏退出 | **正常进入奖励/地图**（HP 74/75、金币 118、第 2 层） |
| 日志里的 NPE 次数 | 2 | **0** |
| 引擎/执行层 | — | 0 次拒绝、0 次执行异常 |

### 33.5 影响面（要如实说明）

自动航行（`CS1_ISOLATED_AUTOPILOT`）是调试用的自动走图功能，玩家正常游玩不走这条路；
玩家手动点地图节点，房间由游戏自己创建，不受这次改动影响。加了保护之后，自动航行在新开局的
地图上会跳过"房间还没建好"的节点（trace 里会出现 `autopilot_map_unlinked_fallback`），
需要玩家自己点一下第一个节点。**崩溃换成"少走一步"，这是有意的取舍。**

## 34. 把第 33 节那道"不崩车但会停住"的保护改成真修：自己把房间补上

### 34.1 33 节留下的问题

33 节的保护是"节点没有房间就跳过"。崩溃没了，但新开局的自动航行会卡在第一个节点上
（trace 里连发 `autopilot_map_unlinked_fallback`）—— 用"停住"换"崩溃"，只是止血。

### 34.2 为什么房间会是空的

再看一眼原版是怎么建房间的。`AbstractDungeon.generateRoom(RoomResult)` 的字节码就是一张表：

```
RoomResult.ELITE    -> new MonsterRoomElite()
RoomResult.MONSTER  -> new MonsterRoom()
RoomResult.SHOP     -> new ShopRoom()
RoomResult.TREASURE -> new TreasureRoom()
RoomResult.EVENT    -> new EventRoom()
```

`MapRoomNode.getRoom()` 只返回字段本身，字段没被创建过就是 null；`nextRoomTransition` 里
那段"建房间"只处理 `instanceof EventRoom` 的情况（把占位的事件房换成抽中的那个）。
换句话说：**地图节点上的房间对象本来就是方框，谁先点谁负责把它装进去，原版是在地图屏幕
点击时装的**。我们的 `AutoPilot.enter()` 抄了"设 nextRoom + 启过场"这一步，漏了"装房间"。

### 34.3 改法

新增 `com.combatsolver1.isolated.TravelRoomFactory`（我们自己的类，源码在
`_build/jar/srcA/`，按 Java 8 编译，major 52）：

```java
public static AbstractRoom create(MapRoomNode node) {
    String symbol = node.getRoomSymbol(Boolean.FALSE);
    switch (symbol) {
        case "M": return new MonsterRoom();
        case "E": return new MonsterRoomElite();
        case "R": return new RestRoom();
        case "$": return new ShopRoom();
        case "T": return new TreasureRoom();
        case "B": return new MonsterRoomBoss();
        default:  return new EventRoom();   // "?" 节点用原版同款占位，过场里会被换成抽中的房间
    }
}
```

`enter()` 的补丁变成"先补房间，补不出来才拒绝"：

```java
if (node == null) return false;
if (node.getRoom() == null) {
    AbstractRoom room = TravelRoomFactory.create(node);
    if (room == null) return false;
    node.room = room;
}
// 原来那三行不变
```

### 34.4 验证（清存档 → 新开 → 自动航行）

```
NPE 次数          0
自动航行           row=0 MonsterRoom → row=1 EventRoom → row=2 EventRoom → row=3 EventRoom
最终状态           GAMEPLAY|GRID|EventRoom/EVENT mapNode=3,1
执行层             0 次拒绝、0 次执行异常
class 载入         loaded=239 failed=0 total=239
```

前一版（33 节）：打完第一场就 NullPointerException；再前一版：不崩但停在第一个节点。
这一版：连走三格、进事件房等人处理 —— 自动航行该有的样子。

### 34.5 说明

事件房、篝火、商店这些照样要玩家自己点（本来就只做战斗自动化），自动航行走到这里就等你，
这是设计而不是卡死。

## 37. "选完牌就停"的真正原因：重采撞在动作队列还没排空的瞬间

第 36 节加了"选完等界面关掉再重采"，但下一轮真机里它还是停了一次。这次把拒绝的原文抓全了：

```
07:34:01.422  PLAY_CARD HEADBUTT hand_slot=2
07:34:01.512  WAITING_FOR_IDLE -> VERIFYING
07:34:03.097  select-gate: screen=GRID cards=2 stillOpen=false after=NONE
07:34:03.098  auto_recapture_refused  status="no report"
07:34:03.106  VERIFYING -> REFUSED -> 自动执行停止
refused 原文：room_phase=COMBAT action_phase=EXECUTING_ACTIONS
             turn=6 actions=1 current_action=present using_card=false
```

关键在最后一行：界面确实关掉了（`stillOpen=false`），但重采要求"当前必须稳定"，
而这一刻动作队列里还剩 **1 个动作、current_action 还在跑** —— 就是你选中的那张牌正在飞向弃牌堆。
所以之前"等界面关掉"不够，得等**动作队列排空**。

### 37.1 改法

`SelectPick.waitForSettle` 的"忙"判据加上第三条：

```java
busy = SelectGlue.pending()            // 选牌界面还开着
    || ChainGate.busy()                // 我们自己的动作门
    || !actionManagerIdle();           // 游戏动作队列里还有活

static boolean actionManagerIdle() {   // actions 空 + currentAction 为 null 才算真闲着
    return am.actions.isEmpty() && am.currentAction == null;
}
```

等待上限从 900 ms 放宽到 1400 ms，安静阈值仍是 120 ms。有上限，不会把渲染线程卡死。

### 37.2 测试探针升级：一次跑四种选牌

```
不设                         完全不动
```

## 38. 拒绝的真正来源找到了：不是选牌界面，是 currentAction 悬着不放

第 37 节按"动作队列没排空"去等，真机上还是被拒。这次把拒绝原文和时机一起抓：

```
13:17:02        选牌界面被解决（HAND_SELECT, 4 张, stillOpen=false）
13:17:02.945    auto_recapture_refused  status="no report"
                当前不是稳定操作点（room_phase=COMBAT action_phase=EXECUTING_ACTIONS
                turn=2 using_card=false current_action=present actions=0
                card_queue=0 monster_queue=0 screen_up=false battle_over=false）
```

注意这三个字段：`actions=0`（队列空）、`screen_up=false`（界面已关）、`current_action=present`
（但 currentAction 这个对象还挂着）。游戏自己的枚举只有两个值 `WAITING_ON_USER` /
`EXECUTING_ACTIONS`，它要等 `currentAction` 被清掉才切回 `WAITING_ON_USER`；而采集侧看到
`EXECUTING_ACTIONS` 就直接判"不是稳定操作点"。

所以：
* 这**不是**选牌界面没关；界面早就关了。
* 也不是"等得不够久"——这个状态会一直挂着，等到上限也不会变。

### 38.1 但这轮修掉了一个更糟的东西

上一版 `SelectPick` 用 `Thread.sleep` 在游戏循环里等（650 ms 展示 + 1400 ms 收尾）。
**在渲染线程里 sleep，等于把游戏自己的 update 冻住**，那个悬着的 `currentAction` 就更不可能被清掉——
等于自己把要等的条件掐死。面板上偶尔的卡顿也来自这里。

现在整段改成"按帧推进、绝不阻塞"：

```java
static void step(IsolatedMctsSession session) {
    if (SelectGlue.pending()) {            // 界面开着：数帧，到 36 帧（约 0.6s）再选
        frames++;
        if (!revealed && frames >= REVEAL_FRAMES) reveal();
        return;                             // 立刻返回，让游戏继续 update
    }
    if (!actionManagerIdle() && settleFrames < SETTLE_MAX_FRAMES && !timedOut()) {
        settleFrames++;                     // 队列没空：下一帧再看
        return;
    }
    reset();
    session.autoVerifyStepRaw();            // 真闲下来了才重采
}
```

上限：240 帧（约 4 s）或 2.5 s 墙钟，先到先算，绝不会把一局拖死。

### 38.2 验证到哪一步

```
13:17:02  screen=HAND_SELECT cards=4 forced=false stillOpen=false after=NONE
          （军备的选牌界面，用新的非阻塞逻辑照样正常选中、正常关闭、没有强推）
```

也就是说：**改成按帧推进没有把选牌功能弄坏**，这是这轮必须排除的回归。
拒绝仍然出现（一局 1 次），但它现在会被自动恢复：`REFUSED → IDLE → SEARCHING` 在 20 ms 内完成，
不会像原来那样停在面板上等玩家。

### 38.3 下一步（下轮做）

真正的收尾是给采集侧补一条：`actions=0 && !usingCard && !screenUp` 时就算稳定，不要求
`currentAction` 必须为 null；或者在重采前把已经 `isDone` 的 `currentAction` 清掉，让游戏自己切相位。
那是 `IsolatedMctsSession` 的字节码，得改补丁，不能像面板那样直接改源码。

## 39. 选牌之后为什么整场卡住：拒绝是终态，得主动放宽/重新上线

### 39.1 现象定量

第 38 节那版（非阻塞按帧推进）在真机上跑出这么一段：

```
13:27:23  选牌界面解决（HAND_SELECT 3 张）→ 同一毫秒 auto_recapture_refused
13:27:23  之后 90 秒：action_executed 一直停在 17，回合仍在 COMBAT
```

也就是说：拒绝之后，自动执行**不会自己回来**。面板每隔几十毫秒还在发搜索请求（`search_request` 8 次），
但没有一次动作提交 —— 玩家看到的就是"选完牌就卡住"。

### 39.2 试错记录（都写清楚，避免以后再走一遍）

| 做法 | 结果 |
| --- | --- |
| 渲染线程里 `Thread.sleep` 等（36/37 节） | 把游戏自己的 update 冻住，要等的状态永远不变；面板还卡顿 |
| 按帧推进、验证推迟到下一帧（38 节） | 选牌界面**再也没被解决**，一局里界面挂了 60 秒 |
| 在验证前直接 `Thread.sleep(650)` 解界面（39 节） | 界面正常解决，但选完立刻重采仍被拒 |
| 手动 pump `actionManager.update()` 排空队列 | 边界拒绝变成另一种采集失败（E-OTHER），仍停 |

结论：**在这条调用栈里没法"等"**——等就是把驱动状态的循环掐掉。

### 39.3 这轮实际改的

1. **去掉在渲染线程里长时间 sleep 等队列**（那是自己掐死自己）。
2. 选牌界面仍保留 650 ms 展示再提交（这个 sleep 是安全的：界面开着的时候游戏本来就在等玩家）。
3. 重采前清掉"已经 `isDone` 但没被 manager 清掉的 `currentAction`"，并在队列空时把相位摆回
   `WAITING_ON_USER`（等于替 manager 早一帧做它本来要做的事）。
4. 万一还是被拒：**调 `session.armAutoExecution()` 重新上线**，让它下一帧再采一次；每个房间最多 3 次。
   这是关键——拒绝是终态，不主动重新上线就永远不会恢复。

### 39.4 本轮验证到哪一步（如实）

* 已验证：选牌界面在新逻辑下**能正常解决**（HAND_SELECT 3 张，`stillOpen=false`，没有强推），
  并且战斗继续（7 个动作、走到下一个房间）。
* **未验证**：重新上线这条路径本身没抓到一次成功恢复。原因在测试侧——这一轮的几次启动先后被
  NVIDIA 控制面板挡住、角色被误选成铁甲战士以外的角色（那个角色本 mod 不支持，面板会直接显示
  "Stopped"）。这些都是我这边的操作问题，不是产品缺陷，但确实让证据链断在这里。

## 40. 选牌卡死的真正机制：手牌选择被"关屏"，没走游戏自己的确认

### 40.1 关键证据链

用 `CS1_SELECT_PROBE=Armaments` 连跑，卡死那局的时序：

```
13:53:43  选牌界面解决（HAND_SELECT 4 张, stillOpen=false）
13:53:43  立刻 auto_recapture_refused
13:53:43 → 13:54:00  面板自动重新上线 8 次（上限），8 次全被拒
13:54:00 之后：action_executed 一直停在 5，回合仍在 COMBAT
```

也就是说：**不是等得不够，是这个动作永远不会结束**。

### 40.2 为什么会这样

`SelectScreenDriver.commit()` 对 HAND_SELECT 的处理是（字节码原文）：

```
手牌选择屏.selectedCards = 选中的牌
手牌选择屏.numSelected  = 张数
调用 refreshSelectedCards()
调用 AbstractDungeon.closeCurrentScreen()      ← 这里
```

它把界面**直接关掉**了。可游戏里打开这个界面的动作（军备、战吼……）是在
`HandCardSelectScreen.update()` 里收到确认回调才会结束的 —— 绕过 update 直接关屏，
那个动作就永远等不到回调，`isDone` 一直是 false，动作队列永远排不空，
采集侧每次看到"正在执行动作"，于是每次都拒绝。**这就是"选完牌就卡住"的机器原理。**

### 40.3 改法：走游戏自己的确认按钮

```java
HandCardSelectScreen screen = AbstractDungeon.handCardSelectScreen;
screen.selectedCards.clear();
选中的牌 → screen.selectedCards.addToTop(...)
screen.numSelected = screen.selectedCards.size();
screen.button.hb.clicked = true;      // 等价于玩家点了"确认"
```

点按钮而不是关屏，游戏下一步自己会跑完 update、回调动作、清队列。

### 40.4 真机结果

```
14:08:36  hand_select confirmed cards=1 via button
之后：动作从 5 → 9，房间从 3,1 走到 4,1，期间 5 次自动航行
```

军备这一场**打完了**、奖励领了、路继续走 —— 这是第 39 节完全做不到的。

### 40.5 仍然存在的

* 选完那一瞬间仍会报一次 `no report`（动作还没跑完），面板会闪一下 Stopped，随后重新上线恢复。

## 41. "无法采集当前战斗状态"的真因：卡牌 UUID 撞车；外加我自己引入的一个崩溃

### 41.1 采集报告给出的原话

```
status: PROTOCOL_REJECTED
error: java.lang.IllegalStateException: card instance identity rejected;
       all observed conflicts: hand[3] d405aaac-...: DUPLICATE_UUID
encounter: Gremlin Nob   turn 2   floor 6   ascension 20
```

手牌里两张牌共用了一个 UUID，采集侧就整场拒绝。这不是"不稳定操作点"那种时序问题，
是**结构性**：同一份快照里出现了两个同 id 的卡牌实例。游戏里 `AbstractCard.makeCopy()`
系列在某些路径会沿用原卡的 UUID，所以这条路任何人都可能撞上。

### 41.2 这轮改的

新增 `SelectPick.repairDuplicateCardUuids()`：采集前遍历手牌/抽牌堆/弃牌堆/消耗堆/limbo，
遇到第二个同 UUID 的卡就把它的 UUID 重新生成一个（卡牌 UUID 本来就该唯一，游戏里没有别的东西依赖旧值）。

真机日志确认它会触发：

```
14:56:21 duplicate card uuid re-rolled id=Strike_R
```

### 41.3 试过头、又退回来的一步（写清楚，别再来一次）

一开始把修复挂成**每帧**执行（想着"随时可能撞车，不能等到 verify"），结果：
同一张 Strike_R 被反复改 UUID，一次运行刷了 **2248 行**。这不只是吵，
更危险的是真卡的 UUID 被反复换掉，采集侧那套 `card_identity_map` 是靠 UUID 认牌的，
换多了会让规划和实际脱节。**已退回"只在选牌确认后修一次"**。

### 41.4 我自己踩出来的崩溃（已修，已验证）

每帧那版挂上之后，游戏一启动就崩：

```
java.lang.NullPointerException
  at com.megacrit.cardcrawl.dungeons.AbstractDungeon.getCurrRoom(AbstractDungeon.java:809)
  at com.combatsolver1.isolated.SelectPick.tickRepair(SelectPick.java:124)
```

主菜单阶段还没有 `currMapNode`，直接调 `getCurrRoom()` 就 NPE。
修法：先判 `currMapNode`/`player` 是否为空，整段包 try/catch —— 一个"修复 tick"绝不该有能力把游戏弄崩。
重新启动验证：`Game crashed` 计数 0，正常进到角色选择。

### 41.5 当前状态

### 42.2 新的卡点：3 哨卫

```
error: IllegalStateException: card instance identity rejected;
       hand[3] 042498fd-...: DUPLICATE_UUID
encounter: 3 Sentries   floor 6
```

### 42.3 关键推理：为什么会反复"修不好"

上一轮我用"重新生成 UUID"来修，结果一次运行刷了 2248 行同样的 re-roll，而且拒绝依旧。
原因现在清楚了：**那不是两张不同的牌共用一个 id，而是同一个卡牌对象同时被列在两个牌堆里**
（手里有它，limbo 里也有 —— limbo 是出牌动画用的临时容器）。

- 重新生成 UUID：改的是同一个对象，两个容器里读到的还是同一个新 id → 冲突照旧，于是每帧再改一次 → 2248 行。
- 所以正确的修法不是改 id，而是**把多出来的那份引用摘掉**。

### 42.4 这轮的修法

`repairDuplicateCardUuids()` 现在分两种情况：

| 情况 | 处理 |
| --- | --- |
| 两个不同的卡牌对象撞了同一个 UUID | 给后者重新生成 UUID（原逻辑） |
| 同一个对象被列在两个牌堆里 | 只在**稳定边界**（动作队列空、无 currentAction）把 `limbo` 里那份多余引用移除 |

`limbo` 是纯表现层容器，且只在稳定边界动手 —— 那个时刻它本来就应该是空的，
里面还有牌说明是出牌动画留下的陈旧引用。

* **未验证**：这条"摘 limbo"的修复是否真能让 3 哨卫那种局面继续打下去 —— 需要再撞一次。

## 45. 受控实验：证明"摘 limbo"这条修法不能上（并已撤回）

### 45.1 为什么要做实验

第 42 节推断"两张重复 UUID 其实是同一个卡牌对象挂在两个牌堆里"，
并据此加了"稳定边界把 limbo 里那份多余引用摘掉"的修法。但一直没机会验证。

这轮加了个**只在测试时生效**的开关 `CS1_DUP_PROBE`：战斗开始那一刻，
把手里最下面那张牌**同时再塞进 limbo**，人为造出完全相同的冲突。

### 45.2 实验记录

```
dup probe armed
dup probe: hand card also placed in limbo id=AscendersBane
stale limbo reference dropped id=AscendersBane        ← 修复按预期触发
refusals = 0                                          ← 采集没有被拒
```

看起来成了。但接着：

```
之后 4 分钟内 action_executed = 0，combat_probe 每秒都在打
```

**战斗卡死了。**

### 45.3 结论

游戏对"这张牌在哪个堆里"是有内部状态的（出牌动画、重抽、洗牌都依赖它）。
我们从 limbo 里摘掉那份引用，采集是干净了，可游戏自己的流程断了。
**一个卡死的战斗比一句诚实的"这场采集不了"更糟。**

因此这一步**已撤回**：现在只在"两个不同对象撞了同一个 UUID"时才改 UUID，
同一对象挂两处则不动，由面板照实说明（第 44 节那三类文案）。

### 45.4 顺带修掉的隐患

实验过程还暴露了 `AbstractDungeon.getCurrRoom()` 会在"地图节点存在但房间还没建好"时抛 NPE。
`tickRepair` / `refusalCause` / 探针三处都加了 `currMapNode.getRoom() != null` 的前置判断。

### 45.5 现状

* `CS1_DUP_PROBE` 保留为测试钩子（不设变量时完全不生效），后续复现同类问题能直接用。
* 实机复跑：撤回后的包正常开局、正常出牌（5 个动作、0 拒绝）。

## 52. 真机抓到一个"卡死"：自动执行停住，且自愈没生效

### 52.1 现象

新开一局（A0），第一场战斗（第 1 层、两只虱子），**5 分钟没有出过一张牌**。面板长这样：

```
Solver  ● Searching
Taken 0   Healed 0   Max HP 0
No route yet
Stopped - could not confirm the fight state, play this turn by hand
Turn 1 | ...
```

`LIVE_SEARCH_TRACE.jsonl` 同时刻记录：

```
combat_probe  phase=REFUSED  stable=true  auto_armed=true  auto_state=SEARCHING
              aborted_key=NeowRoom@-1,0  reset_count=1
```

### 52.2 根因

我第 43 节写的自愈 `maybeReArm()`，触发条件是**状态名里含 `REFUS`**：

```java
if (state == null || !state.contains("REFUS")) return false;
```

但这次会话报的状态是 `SEARCHING`，被拒的标记在 **phase** 字段上（`phase=REFUSED`）。
于是自愈条件不成立，一次都没重挂 —— 面板就一直停在"搜索中 + 打不了"。
这就是用户说的"停住"那一类，只是触发路径比我原来想的多一种。

### 52.3 修法

判据从"状态名"改成两条任一成立：

1. 状态名含 `REFUS`（原有逻辑）；
2. **停滞**：面板已经在显示一条 problem/refusal 文案，并且距离上一次真正执行动作超过 9 秒。

同时把重挂预算从 8 次提到 40 次（按动作数重置），避免"重试几次就永久放弃"。

新增日志 `re-arm after refusal #n/40`，落在 `panel-layout.log`，以后能直接看出它有没有动。

### 52.4 验证

改完重新起一局 A0：

* 3 分钟内 **19 个动作、0 次采集拒绝**，一路打到第 5 层休息点
* 不再是"第一场就停住"

（这次没触发重挂也没关系——说明这条路径上采集本身是通的；停滞规则是兜底。）

## §53 中文环境根因（2026-11-04 深夜）

## §56 药水在求解器里的真实状态（2026-11-05 00:12）

用户要求「药水也是求解器决策的一部分」。查下来不是没做，而是**做了外壳、缺内核**：

* mod 侧有完整的药水计划设施：`PotionPlanSet`（score / potionsUsed）、`IsolatedMctsSession.potionPlans()`、
  `switchPotionPlan()`，以及 6 个环境开关（`CS1_ISOLATED_ALLOW_POTION_EXECUTION`、`CS1_ISOLATED_COMPARE_POTIONS`、
  `CS1_ISOLATED_EXECUTION_POTIONS`、`CS1_ISOLATED_ONE_POTION_ONLY`、`CS1_ISOLATED_STOP_AFTER_POTION`、`CS1_ISOLATED_POTION_PROBE`）。
* 打开 `ALLOW_POTION_EXECUTION+COMPARE_POTIONS` 后确实会记录 `potion_plans_compared`，
  但每个计划的 `potions=0`——**没有任何方案真的喝药**。
* 外部引擎 `s2b0_search_3d.exe` 里写死了 `potion_actions_mode` 的取值 `off`，即该构建不模拟药水动作。
* 换成本地 Java 搜索（去掉 `engine.path`）再试，`potion_plans_compared` 依旧 `potions=0`——
  两条引擎路径都不建模药水，`usePotion` 只是给执行层准备的，没有进入搜索空间。

**结论**：让药水真正进入决策，需要在搜索引擎里实现药水效果（`vendor/sts_lightspeed` 的 C++ 侧），
工作量约为「新增一类动作 + 每种药水一个效果分支 + 与现有估值对齐」，属于第二轮里最大的一块，
且必须重新编译 exe。可选折中：在面板上给出启发式建议（例如精英/Boss 战前喝力量药），
但那不是搜索结果，属于人工规则，需用户认可后才做。

## §65 药水为什么进不了搜索（2026-11-05 03:05）

## §85 字节码补丁终于能用了：问题出在没转发 visitMaxs（2026-11-05 07:50）

一整天卡在 `VerifyError` / `ClassFormatError`，真正的原因极蠢：
自定义的 `MethodVisitor` **没有转发 `visitMaxs` / `visitCode` / `visitEnd`**，
于是重写出来的方法 `max_locals = 0`，JVM 报
`Arguments can't fit into locals in class file`。补上转发后立刻正常。

顺带确认了几条规律（记下来省得再踩）：
* `ClassWriter(new ClassReader(data), 0)` 和 `accept` 必须用**同一个 reader**，
  两个实例会写出坏 class
* 改控制流（`GOTO`）一定要 `COMPUTE_FRAMES` + `getCommonSuperClass` 读游戏 jar，
  否则 `Inconsistent stackmap frames`
* **不改控制流**的写法最稳：把 `"X".equals(y)` 换成 `POP;POP;ICONST_1`，
  栈形状不变、帧不用重算。注意 javac 常在 receiver 和 call 之间插参数，
  所以要按"最近 6 条指令内出现过该字面量"来匹配，不能只认紧邻。

**已经打进去的两处放宽**（`ForceEquals2`）：
* 双虱子 `"2 Louse"` 比较不再要求等于 → 2 个点
* 卡牌 `"ASCENDERS_BANE"` 比较 → 1 个点

**实测**：`loaded=365 failed=0`，跑起来 **0 次采集拒绝**（之前是 40 次），
但随即撞到下一个坑：

```
java.lang.NoSuchFieldException: isBattleLower
```

这个字段名在我们 jar、BaseMod、StSLib、desktop-1.0.jar 里**都搜不到**，
说明是运行时拼出来的（`getDeclaredField(...)` 的实参由几段字符串拼接）。
下轮就从这里查：谁在反射 `isBattleLower`，它想读什么。

## §90 引擎其实跑的是 rollout 策略，不是树搜索（2026-11-05 08:55）

* 掉血预测不可信

## §94 第③条：事件里的战斗也能采集了（2026-11-05 09:35）

## §97 搜索预算实验 + 硬超时保护（2026-11-05 09:55）

## §100 三个卡死点（2026-11-05 11:20）

用 jstack 抓到了主线程的真实停点，逐个说：

### 1. 面板每帧读搜索结果文件（已修）

```
"LWJGL Application" RUNNABLE
  at IsolatedMctsPanel.lastResultRoute(IsolatedMctsPanel.java:790)
  at IsolatedMctsPanel.draw(...)
```

`draw()` 里每帧都在扫目录、读最新 `SEARCH_RESULT.*.json` 并用 gson 解析，
还每帧 `CardLibrary.getCard` 建卡牌对象。渲染线程被拖垮，看起来像"卡死"。

改法：轮询节流到 500 ms，卡牌名加 HashMap 缓存。

### 2. 死亡重开只按一次"开始游戏"（已修）

`CardCrawlGame.startOver()` 只回主菜单。原先重开后按一次就放弃，
而且判断"是否已开局"用的是 `dungeon != null`——刚重开时旧 dungeon 还在，
于是标记立刻被清掉，游戏永远停在标题画面。

改法：`wantNewRun` 标志 + 每帧重按，直到出现"血量>0 的新玩家"才停。

### 3. COMBUST（燃烧）导致整场拒绝采集（已中和）

```
E-CAPTURE-POWERS COMBUST drives a player counter whose native value the protocol cannot read
```

`potion_actions` 字段仍是 `{}`（那是旧协议占位），真正的方案在 `plan_potions` 里。

### 二、修掉一个执行侧 bug

方案可以在同一回合列出两瓶（上面血瓶×2 就是）。原来的 `PanelTick.plannedSlot()`
每次只返回"方案里第一条匹配当前回合的槽位"，喝完 0 号槽后槽位变成空的 `PotionSlot`，

现在遍历方案时会跳过已经是空槽的项，直接找下一瓶还没喝的。

### 三、执行时序

`currentTurn()` 用 `actionManager.turn + 1`，与引擎 `plan_potions[].turn`（从 1 开始）对齐；
两瓶之间有 1.5 秒间隔，不会一帧连喝两瓶。

## §114 第③条（事件战斗也要给路线）的代码依据（2026-11-05 21:05）

用户担心的是"事件里打起来的架不采集"。逐行看过载入路径，结论：**没有任何按房间类型过滤的地方**。

### 1. 面板的在场判断

`IsolatedMctsPanel.inCombatOrReward()`：

```java
if (room.phase == AbstractRoom.RoomPhase.COMBAT) return true;
if (room.phase != AbstractRoom.RoomPhase.COMPLETE) return false;
return AbstractDungeon.screen == AbstractDungeon.CurrentScreen.COMBAT_REWARD;
```

只看 `RoomPhase`，不看 `room.getClass()`。EventRoom 里打起来时 phase 就是 COMBAT，
所以斗兽场（Colosseum）、心智绽放（Mind Bloom）、蛇之试炼这类事件战斗和普通怪一样进面板。

### 2. 谁发起搜索

`render()` 每帧调 `maybeKickIdleSearch()`；后者同样只判断 `room.phase != COMBAT` 就退出，
否则每个房间踢一次 `session.requestSearch("panel-kick")`（`REARM_GAP_MS` 防抖）。

```java
if (room == null || room.phase != AbstractRoom.RoomPhase.COMBAT) { ... return false; }
...
session.requestSearch("panel-kick");
```

### 3. 采集端认不认事件战斗

`LiveStateV1Capture` 会把房间信息写成：

```json
"room_context": {
  "kind": "MAP_MONSTER",
  "class": "com.megacrit.cardcrawl.rooms.MonsterRoom",
  "elite_trigger": false,
  "event_class": null,
  "event_encounter": null,
  "event_enemy_index": null
}
```

`event_class` / `event_encounter` / `event_enemy_index` 三个字段本来就是为事件战斗留的，
普通怪房间是 null。

### 4. 引擎侧

用一份 `kind=EVENT_COMBAT`、`class=EventRoom`、`event_class=...MindBloom`、
`event_encounter=3 Darklings` 的状态跑引擎：

```
status SEARCHED | outcome PLAYER_VICTORY | steps 5
```

引擎不看房间类型，只看战斗状态本身。

### 结论

第③条在代码路径上没有缺口。**所谓"事件战斗没路线"更可能是别的房间（地图/事件/商店）
不画面板**——那是设计上就该隐藏（用户自己要求"非战斗房间隐藏面板"）。

## §115 六按钮布局的几何自检（第⑥条，2026-11-05 21:10）

3. 面板高度公式 `PAD*2 + 26 + 44 + 4 + 12 + ROW + ahead*(ROW-4) + 2 + 18 + (BTN_H+8) + BTN_H`

## §118 面板跑到屏幕外面去了（真正的"看不见"原因，2026-11-05 21:20）

### 证据

改完分辨率重启后，`panel-layout.log` 记了一条：

```
Thu Nov 05 21:13:56 layout panel x=561 y=768 width=316 opacity=55% window=1360x768 height=213
```

`y=768`、`window=1360x768` —— 面板的顶部锚点正好等于窗口高度，**整块面板落在屏幕下边缘之外**。
它确实在画（日志就是画的时候写的），只是画在了看不见的地方。

### 原因

```java
private static float anchorY(SolverSettings settings) {
    float stored = settings.panelY();
    if (stored > 0f) return Math.min(stored, Settings.HEIGHT);   // ← 只按上界夹
    return Settings.HEIGHT * 0.855f;
}
```

`panelY` 是**拖拽后存进设置的绝对坐标**。用户在 1280x960 的时候把面板拖到底部，
存了 838；窗口变成 768 高以后，`Math.min(838, 768) = 768` —— 顶部贴在窗口最底边，
面板整体（高 213）全在屏幕外。

### 修法

在 `draw()` 里按"整块面板必须落在可视区"来夹，而不是只夹锚点：

```java
top = Math.min(top, Settings.HEIGHT - PAD * s);
if (h + PAD * s * 2f <= Settings.HEIGHT) top = Math.max(top, h + PAD * s);
float y = top - h;
```

窗口变小时面板会自己回到屏幕内，不会再"画了但看不见"。

### 这条和用户报的"UI 有问题"对得上

用户之前看到的可能是：面板有时候在、有时候不在（取决于他之前拖到哪儿、窗口多大）。
现在不管怎么改分辨率、怎么拖，面板都会被夹回可视区。

## §127 真正的根因：VerifyError 让采集层整个崩掉（2026-11-06 06:25）

用户 06:04 再次反馈「还是没有反应，路线求解也不对了」，并给出新开一局（Dad、99 金、
第 1 层）的截图：面板文字重叠、只有零散两行路线。

### 诊断

先看日志文件时间：`panel-layout.log` 一直写到 06:08，但 `LIVE_SEARCH_TRACE.jsonl` 停在
04:13、所有 `SEARCH_RESULT.*.json` 都是 04:02 的旧文件 —— **这一局从头到尾没有跑过一次
求解**。而 `panel-layout.log` 里 `button click i=0` 出现了 91 次，说明按钮点击是有效的，
"没反应"是表象。

为了看清状态，在 `render()` 里加了 `diag()`（每 2 秒一行 state / problem / screen / room /
plan / drive / kicks / arms / drives / opening）。用用户 06:02 的存档重启后读到：

```
06:21:09 diag state=IDLE problem=E-INTERNAL java.lang.VerifyError: Inconsistent ...
         screen=NONE room=2147257305 plan=null drive=false kicks=1 arms=0 drives=0
```

### 根因

§126 里为放宽 `invalid or duplicate full card UUID` 这个致命检查，ASM 把
`Set.add(...)` 后面的 `ifne OK` 改成了 `goto OK`，使 `new IllegalStateException ... athrow`
整段变成不可达代码。**JVM 的栈图（StackMapTable）仍把 THROW 标记为分支目标**，于是游戏
真正执行到 `LiveStateV1Capture` 的这段方法时抛
`java.lang.VerifyError: Inconsistent stackmap frames`。

之前的 `-Xverify:all` LoadAll2 冒烟测试只加载/链接类、不执行方法，所以没发现；这也是为什么
一连串 r8→r21 版本都"看起来通过校验"却在真机上完全不求解。采集层一崩 → 不写
`live-battle-state-v1.json` → 引擎不运行 → 没有 `SEARCH_RESULT` → 面板只能显示兜底文本、
按钮点了像没反应、战损/路线全部不对。**用户连着三轮反馈的所有症状，都是这一个回归 bug。**

### 修法（`RelaxFullUuid2`）

不再改控制流形状。只在 `ifne OK` 前插入 `pop; iconst_1`：丢掉 `Set.add` 的真实布尔值、
压入常量 1，条件恒真、合法重复 uuid 被容忍，而
- 栈高不变（pop 一个 int、push 一个 int）
- 每个分支目标仍然存在、每个 stackmap frame 仍然描述可达偏移
- `ClassWriter(cr, 0)` 原样输出，不重算帧

字节码确认：

```
1840: invokeinterface Set.add:(...)Z
1845: pop
1846: iconst_1
1847: ifne          1879
1850: new           #191  // java/lang/IllegalStateException
```
