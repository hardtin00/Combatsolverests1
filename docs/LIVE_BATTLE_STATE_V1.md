# `live_battle_state` v1 — field contract

Status: partial offline interoperability prototype; not a completed real-game input path. The Java runtime collector can emit a canonical v1 snapshot only for its strict supported state and room allowlists; the real EventRoom path has not yet produced a protocol file. Offline fixtures exercise Java serialization, C++ root restoration, `STATE0_DETAIL`, and a battle-only search entry. The path-shape inventory is in `LIVE_BATTLE_STATE_V1_FIELD_AUDIT.md`; fixture results are synthetic and do not constitute live round-trip evidence.

## Trust boundary

The snapshot is accepted only at a stable `PLAYER_NORMAL` boundary: player turn, no current card, no queued actions/cards, no pending native choice, and no monster action resolving. The Java collector reads before and after; a changed battle identity or changed source fingerprint invalidates the whole snapshot. Missing, null, unknown, out-of-range, or unsupported values are errors. No field is defaulted from `LiveCapture` or inferred from a disk save.

The runtime Java producer currently narrows this further to the untouched first player turn (`turn=1`, no cards played, no combat damage/discards), no player powers, only the Ironclad `Burning Blood` relic, and card/potion/Sentry states supported by the explicit mappers. This keeps C++ turn/power counters at their proven initial values; any other live root is rejected. STS1 has no `last_targeted_monster` player field. That wire member is omitted only when `SURROUNDED` is absent; C++ retains its existing internal sentinel in that case and rejects an omitted target if `SURROUNDED` is present. This is not a reconstructed game value.

The wire format is UTF-8 JSON with `protocol: "live_battle_state"`, integer `version: 1`, and top-level `capture_id`, run seed, character, act/floor, encounter, turn identity, and required `room_context`. `capture_id` is an independent UUID for correlating one serialization transaction; it is not an STS1 native battle ID and does not authorize execution. The Java writer binds it to the exact serialized bytes in a `.capture.json` sidecar containing SHA-256. Card UUIDs remain 128-bit strings at the wire/differential layer; the importer assigns dense engine `uniqueId`s and validates a bijection across the four piles. Truncating a game UUID to `CardInstance::uniqueId` is forbidden.

`act` is copied as an integer from static `AbstractDungeon.actNum` into `BattleContext.act` and read back by `STATE0_DETAIL`; it is retained as run metadata and is not currently consumed by combat transitions after the initial live state is restored. `monsterTurnIdx` is a C++ MonsterGroup traversal cursor, not an STS1 field, and is not part of the wire protocol. At a validated stable player-action root, the cursor is not necessarily the same value in the original running engine: first player input starts at sentinel 6, while later player inputs retain the terminal group count (3 for three Sentries). This does not affect the restored root because the cursor is not read during player actions and every accepted end-turn action resets it to 0 before `executeActions()` can enter the monster traversal loop. The importer initializes the internal cursor to sentinel 6; a regression compares both boundary representations through the actual reset and verifies the same slot order and Sentry turn effects. This applies only to the accepted idle player boundary (`PLAYER_NORMAL`, empty queues, no ended/skip turn); it is not a general reconstruction of an in-flight monster phase.

## Initial allowlist and rejection policy

The parser accepts vanilla Ironclad at a stable player-normal boundary from either the existing map-origin `THREE_SENTRIES` elite path or one narrowly allowlisted event origin. The event path requires the concrete `EventRoom` class, `kind=EVENT`, `elite_trigger=true`, exact `DeadAdventurer` class, enemy index 0, and event encounter name `3 Sentries`. STS1 bytecode shows that this branch calls `MonsterHelper.getEncounter(getMonster())`, while `AbstractEvent.enterCombat()` sets combat phase and initializes the current room's monster group. The root still validates all three exact vanilla Sentry instances and their current state. C++ stores the two origins separately; event provenance is never normalized to `MonsterRoomElite`.

The new `mcts_state_search` entry searches only a restored `BattleContext`, verifies that its returned action sequence reaches a battle outcome, and does not create or advance `GameContext`. A battle victory is therefore the terminal result for this search. It does not run `BattleContext::exitBattle()`, `GameContext::afterBattle()`, Dead Adventurer's continuation, or map elite rewards. Event phase/reward state and post-battle reward RNG remain outside this combat-only protocol scope; a combat win is not a complete route result. Other EventRoom origins, Dead Adventurer enemy indices, encounters, or rosters remain rejected. These are source/bytecode and offline test boundaries; a real EventRoom snapshot still requires a separate live capture and C++ differential.

The parser rejects unknown cards, relics, potions, powers, moves, unresolved selections, extra queue work, and any state requiring an unsupported field. For Sentry, the Java boundary maps the exact runtime class and ID, preserves the original MonsterGroup slot, maps native move IDs `3` (debuff/Dazed insertion) and `4` (attack/Beam) to `SENTRY_BOLT` and `SENTRY_BEAM`, and reverses the tail of `AbstractMonster.moveHistory` because the game appends newest moves while the C++ model stores newest first. If only one native move exists, the older C++ slot is the explicit `INVALID` sentinel. Only exact `ArtifactPower`/`Artifact`, `WeakPower`/`Weakened`, and `VulnerablePower`/`Vulnerable` pairs are translated; Weak and Vulnerable carry the concrete instance `justApplied` value, while Artifact's C++ transition has no timing bit. Unknown powers and moves reject. The serializer reads `firstMove`, `beamDmg`, and `dazedAmt` from the Sentry object; C++ accepts only `first_move=false` and verifies the two damage parameters against ascension. Sentry unique-power and misc slots are required to be zero because the supported Sentry model does not use those counters. Other monsters require their own evidence-backed translator. The old experimental `battle_counters` object is rejected: the three search counters are initialized internally, and caller-supplied `misc_bits` is not trusted.

The importer must construct a fresh `BattleContext` by assigning decoded state. It must not call `GameContext::initFromSave`, `BattleContext::init`, encounter construction, shuffle, HP rolls, or RNG methods. `mcts_save` and replay commands remain unchanged. This is a pre-release correction to the partial v1 prototype schema; there is no Java producer or released v1 snapshot compatibility promise yet. Existing experimental JSON containing `battle_counters` is intentionally rejected and must be regenerated with `room_context` provenance.

The diagnostic probe refuses non-Ironclad players, unsupported room/event provenance, and any roster member that is not the exact vanilla Sentry class/ID. Its source capture records `room_context` and a full UUID-to-dense-ID map in hand/draw/discard/exhaust iteration order, rejecting duplicate UUIDs. The event-origin fixture validates serializer/parser plumbing only; it does not prove that a real EventRoom C++ root matches a live game.

Card instance state support and card-effect support are separate gates. The diagnostic report (not the v1 wire protocol) carries per-instance classification and mapping reasons for every enumerated card, even if one ID or state cannot be mapped. `writeProtocol` remains fail-closed and the C++ importer independently accepts only the same narrow allowlist; a diagnostic report can never be used as an engine input. Havoc's exact native identity and common fields are now mapped, while search eligibility relies on the pre-existing C++ Havoc branch; implementation presence is not an L4 validation. No schema version or execution authorization changed.

The 2026-10-20 offline card slice also maps native `Shrug It Off` to `SHRUG_IT_OFF`. Its source instance must have `misc=0` and `ethereal=false`; UUID, cost, cost-for-turn, 0/1 upgrade state, free-to-play, and retain continue through the generic strict card serializer. The C++ importer restores the instance and `STATE0_DETAIL_CARD` reads it back; the pre-existing C++ effect branch grants 8/11 block and queues one draw. This is synthetic L2 interop only; it does not validate a live combat snapshot or the random draw against the game.

### Player power timing field

`just_applied` is conditional, not a universal `AbstractPower` property. The installed STS1 bytecode declares a private, non-static boolean on `WeakPower`, `FrailPower`, `VulnerablePower`, `DoubleDamagePower`, and `DrawReductionPower`; each overrides `atEndOfRound()`. The diagnostic collector reads it reflectively from those exact concrete classes, verifies the native `ID` against bytecode-confirmed strings (`Weakened`, `Frail`, `Vulnerable`, `Double Damage`, `Draw Reduction`), and maps them explicitly to C++ `WEAK`, `FRAIL`, `VULNERABLE`, `DOUBLE_DAMAGE`, and `DRAW_REDUCTION`. The first four statuses skip their end-of-round decrement once and clear the bit when newly applied; `DrawReductionPower` uses the bit in C++ at the next-turn draw adjustment to defer expiration once. `IntangiblePlayerPower` has no such field, and the C++ model decrements INTANGIBLE unconditionally, so `just_applied` is not applicable to that status. Missing flags on the five timing-sensitive statuses, flags on other statuses, unknown status IDs, class/ID mismatches, or attempts to serialize a timing flag from an unrecognized class are rejected; the parser does not substitute false. This mapping has bytecode and offline transition-test evidence only; no live player-power sample was collected in this task.

## Acceptance diff

`STATE0_DETAIL` must emit every mapped field structurally: player primitive fields/statuses/counters; each pile in order with card ID, UUID, upgrade, costs, special data and flags; relics/counters; potion slots; each monster's original slot, identity, HP/block, move/history, status values, unique powers and AI fields; all six RNG seed pairs/counters; turn/stage/counters. Java compares parsed fields to the recovered C++ structure. A compact STATE0 or a hash alone is insufficient.

Current offline validation invokes `LiveBattleStateV1OfflineProducer` only with the fixture carrying `test_only=OFFLINE_FIXTURE_NOT_REAL_GAME_STATE`. It strips that marker, writes the canonical JSON through the Java writer, then passes the generated file to C++ `mcts_state`. `live-state-v1-full-diff.ps1` reconciles each of 155 normalized path shapes against C++ detail output; any omitted field remains `UNAVAILABLE`, and empty-array shapes are `NOT_APPLICABLE`. This remains fixture-only L2 evidence, not a complete live-state or real-game comparison. See `build/live-state-validation/live-state-v1-full-field-diff.txt` after running the focused test.
